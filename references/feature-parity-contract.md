# Feature parity contract

This contract captures reusable interaction architecture from the canonical local walkthrough.
It excludes its query text, plan payloads, internal content, and fixed source revision. The
machine-readable companion is
[feature-parity-inventory.json](feature-parity-inventory.json).

The previous renderer supplied a stage rail, a small action rail, one before/after view, a
physical tree, and a basic execution event. It lacked the canonical overview, substep,
traversal, artifact, experiment, deep-dive, boundary, execution-memory, and network-status

visualization family. Its `previous_sample_gaps` list is the enforced semantic delta from the
deficient output; byte and tag counts are diagnostic baselines, not parity substitutes.

## Required global surfaces

Every generated page must expose the semantic feature IDs listed in the JSON inventory:

- ten-stage navigation;
- a collapsible stage overview with input, output, owner, exclusions, and handoff;
- query-specific substep cards with behavior, change, and runner-count badges;
- previous, next, and range navigation that updates content in place;
- detailed what/why/debug/next/source/method-path content;
- linked traversal nodes with current, movement, return, and next state plus
  previous/play/range/next controls;
- collapsible before/after artifacts with linked operators;
- a stateful outbound-source beacon showing state, route, and purpose;
- keyboard navigation, visible focus, responsive layouts, reduced-motion behavior, and print
  output.

## Mandatory per-substep runner

Every complete-model substep has exactly one runner. No-op phases are retained and use the
same phase-appropriate runner with explicit evidence gates and reasons. A runner must have:

- reset, previous, next, apply/execute, range, and action-rail controls;
- two or more distinct visible snapshots;
- before/after state, progress, result, and exact source;
- one or more interactive experiments with option-specific results;
- no inert controls.

The validator rejects missing runners, mismatched runner types, duplicate snapshots,
unexplained no-ops, pass outcome contradictions, and incomplete source grounding.

## Specialized systems

### Compiler

Syntax, Semantic, and Relop substeps use compiler runners. They show action states, progress,
exact source, unique experiments, and semantic or CSL-to-Relop mapping where applicable.

### Pass pipeline

Preparation and all optimization phases use pass runners. Only passes applicable to this query
may appear. Each pass includes traversal, predicate, applicability, optimization target,
cumulative colored diff, source, rule, and result. A scheduled pass with an unchanged tree is
explicitly `SCHEDULED_NO_OP`, never a claimed transformation.

### Physical plan

Every physical substep has its own runner and input-contract collapse. The deep dive carries
the complete evidenced plan, linked operators, logical-to-physical mapping, schemas, node IDs,
key indexes, execution/Rust eligibility, target scope, remote metadata, and only those raw
sections allowed by the evidence policy.

### Serialize/native boundary

Every boundary substep has a runner with managed, JSON, UTF-8, and native lanes; object/JSON/
byte views; evidenced node ranges; context comparisons; failure injection; and a debugger map.

### Execute

Every query-present runtime operator or boundary has a runner. It includes a user-driven
timeline, language lanes, what/why/stack/heap effects, cumulative conceptual stack (top first),
applicable lifetime zones and states, and active/waiting/not-created components below stack
and heap. It also exposes failure, cancellation, memory, and lifetime scenarios, pull/data
direction, current ownership, and next breakpoint.

## Evidence and safety

All action, traversal, artifact, operator, frame, zone, component, scenario, and experiment
links are exact-line Azure DevOps HTTPS URLs pinned to the authorized workspace HEAD. The
renderer does not execute the supplied query. Unsupported claims remain visibly `ESTIMATED`.
The page is a self-contained offline artifact and model text is embedded with script-safe JSON
escaping and rendered through `textContent`.
